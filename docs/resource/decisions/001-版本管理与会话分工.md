# 001 版本管理与会话分工

日期：2026-11-23

状态：已采用。2026-11-23 在 [INC-002 首次转交](../../开发记录/INC-002.md#第一次发送)后调整了开发仓库的边界。

用户会单独开一个应用开发会话，同时希望能在 phase2 按轮次回滚。一次增量既改变软件，也可能改变需求说明和验收记录，回看时需要找到同一时点的两者。

开发和审查使用同一份应用文件，各有自己的 Git 根。开发者从 `classwork-repo/` 新开聊天，只收到业务需求，在自己的仓库实现、测试和提交。该仓库的首个提交取自当时的应用文件。审查者在 `classwork-phase2/` 核对交付，把应用文件和轮次档案一起提交，负责按轮次查找或回滚。外层直接跟踪应用文件，新增文件也按实际路径暂存。

重新检出整个工作区时，开发仓库的本地 Git 历史需要单独恢复。若从当前交付版本重新起步，在干净的检出中由审查者先运行以下 PowerShell 命令，为已跟踪的应用文件建立基线。

```powershell
git -C classwork-repo init -b main
git -c core.quotePath=false ls-files -- classwork-repo | ForEach-Object { git -C classwork-repo add -- $_.Substring('classwork-repo/'.Length) }
git -C classwork-repo commit -m "chore: 建立应用开发基线"
git -C classwork-repo rev-parse --show-toplevel
```

最后一条应返回以 `classwork-repo` 结尾的路径。已读过外层资料的聊天保留原上下文，切换开发入口时另开空白聊天。

本次在应用目录用 `codex debug prompt-input` 对照检查。调整前同时加载了开发和审查两份项目指令，调整后只加载开发指令。开发 Git 日志从应用基线 `aa4ad90` 开始。若聊天启用完全访问权限，工具仍可主动读取父目录。

决策、架构、需求与计划归入 [docs/resource/](../README.md)。开发记录另外保留各轮收到的提示词、当时遇到的问题和实测效果，便于按时间复查。
